## 調査で判明した「ブログが無い」理由

制作会社がブログ機能を **作りかけのまま納品** している。

| ファイル / 設定 | 状態 |
|---|---|
| `home.php`（記事一覧） | **中身が空**。`get_header()` と `get_footer()` のみ |
| `single-post.php`（記事個別） | ほぼ完成。ただし日付が `2023.10.01` 固定、サムネイルが `dummy.jpg` 固定 |
| 設定 → 表示設定 → 投稿ページ | **未設定**（`— 選択 —`）。これが「ブログのタブが無い」直接原因 |
| `functions.php` | `is_home()` のとき アーカイブタイトルを「ブログ」にする処理あり＝**ブログ運用は想定されていた** |

補助的な事実：

- `add_theme_support('post-thumbnails')` 済み → アイキャッチ画像は使える
- `add_theme_support('title-tag')` 済み → titleタグは自動生成
- `excerpt_length` = 80文字、`excerpt_more` = `...`
- `archive-works.php` が `wp_pagenavi()` を呼ぶが **WP-PageNavi は未インストール**
  → 本パッチではコア関数 `the_posts_pagination()` を使用
- `parts-bread.php` が `bcn_display()` を呼ぶが **Breadcrumb NavXT は未インストール**
  → パンくずは表示されない（`function_exists` で保護済みなのでエラーにはならない）

### ⚠️ 404が全てトップへ301リダイレクトされる

`functions.php` に以下があり、**存在しないURLは全てトップページへ301で飛ばされる**。

```php
add_action( 'template_redirect', 'is404_redirect' );
function is404_redirect() {
  if ( is_404() ) { wp_safe_redirect( home_url( '/' ), 301 ); exit(); }
}
```

作業上の影響：

1. ブログURLの設定ミスに気づきにくい（404ではなくトップが出る）
2. **301はブラウザに強くキャッシュされる。** 設定前に該当URLを開くと、
   設定後もトップに飛び続ける。検証はシークレットウィンドウで行うこと
3. SEO的にはソフト404扱いで好ましくない（別途改善を提案する）

### 検証方法

本番に適用する前に、`php -l` での構文チェックに加え、WordPress関数をスタブ化した
ハーネスで実際に実行し、以下を確認している。

- 実行時エラー・警告ゼロ（`E_ALL`）
- 記事0件／ページ送り無し／アイキャッチ無し／カテゴリ無しの各異常系
- タイトルへのXSS混入がエスケープされること
- `archive-works.php` とレンダリング結果のマークアップ骨格が一致すること
  （タグ＋class を順に抽出して diff。ページ送り以外は完全一致）

### 設計方針：CSSは1行も足さない

`assets/css/style.css` はコンパイル済みの単一ファイルで、手編集は危険。
そのため `home.php` は **`archive-works.php` と同じクラス名（`p-worksArchive__*`）を
そのまま流用**している。新しいクラスを作らないので、CSSを触らずに
制作実績一覧と同じ見た目が出る。

本番のブログ運用が固まった段階で、`p-blogArchive__*` への分離を検討する。

### home.php の主な実装判断

- **メインクエリ（`have_posts()`）を使用。** `archive-works.php` のような
  `new WP_Query` は使わない。`home.php` ではメインクエリがそのまま投稿一覧になり、
  「表示設定 → アーカイブページに表示する最新の投稿数（10件）」とページ送りが正しく効く
- 制作実績カードの「クライアント / 制作年」の位置に **投稿日**（`Y.m.d`）を表示
- カテゴリを chip として表示
- アイキャッチ未設定時は `assets/images/dummy-works.png` にフォールバック
- ページ送りは `the_posts_pagination()`。`.p-pagenavi` でラップし、
  テーマ側にCSSがあれば拾われるようにしてある

## `/member/` の顔写真がプレースホルダになる（2026-09-21）

### 症状

`archive.php` の HTTP 500 を直した直後、`/member/` は表示されるように
なったが、**顔写真が全員ロゴ画像（ogp-b.png）に化けていた。**

### 原因

**メンバーの写真はアイキャッチではなく ACF の画像フィールド**に入っている。
`archive.php` は `get_the_post_thumbnail_url()` しか見ていないため
「アイキャッチ無し」と判定してフォールバック画像を出していた。

トップページの `#member` セクションは ACF を直接読んでいるので正しく出る。
だから「写真が変わってしまった」ように見えた。

### 対応

`marketik_archive_card_image()` を追加し、次の順で解決する。

1. アイキャッチ
2. ACF の画像フィールド（`get_fields()` を走査。**フィールド名に依存しない**）
3. 投稿に添付された画像の1枚目
4. プレースホルダ

ACF の返り値形式は設定によって「配列／添付ID／URL」の3通りに変わるため
`marketik_image_url_from_value()` で3通りとも扱う。
**リンクフィールドも `url` キーを持つ**ので、`mime_type` が `image/` で
始まるか `sizes` があるかで画像判定している。

スタブ環境で12ケース検証済み（アイキャッチ優先・ACFの3形式・ギャラリー・
リンク誤認防止・電話番号の数値誤認防止・ACF未導入時・添付フォールバック）。

あわせてカスタム投稿タイプの一覧では投稿日を出さないようにした
（`2026.06.12` は入社日ではなくデータ登録日で、意味が無いため）。

### `archive.php` と `index.php` の関係

`index.php` は `archive.php` の完全なコピー（冒頭コメントのみ相違）。
同名関数の二重定義を避けるため、ヘルパーは
`if ( ! function_exists( 'marketik_archive_card_image' ) ) :` で囲ってある。
**片方を直したらもう片方も同じ内容にすること。**

### ナビとの関係（`/member/` は孤立ページ）

ヘッダー・ドロワー・フッターの `Member` は `/member/` ではなく
**トップページの `#member`** を指している。
`/member/` は CPT の `has_archive` で生えているだけで、サイト内のどこからも
リンクされていない。AIOSEO が `member-sitemap.xml` を出しているため
Google だけが見に来ていた。

将来 `/member/山崎-雅浩/` を著者プロフィール（E-E-A-T用）として使う方針なので
noindex にはせず、正しく表示する方向で直した。

## 新メンバーへの連携展開（2026-09-21）

高橋啓吾さんにも下書き投稿環境を用意するため、手順書
`SETUP-new-member.md` を作成した。**そのまま本人に渡せる形**にしてある。

### 設計方針

| 方針 | 理由 |
|---|---|
| **人ごとに WordPress ユーザーを作る** | アプリケーションパスワードはユーザーの権限をそのまま引き継ぐ。漏れたとき1本だけ取り消せるようにする |
| **権限は寄稿者で固定** | 公開できない状態を保つ。`status=draft` 固定と合わせて二重の歯止め |
| **パスワードは本人が発行し、誰にも渡さない** | 山崎も受け取らない。AIのチャットにも貼らせない |
| **設定ファイルは `chmod 600` を先に当ててから書く** | 一瞬でも他ユーザーから読める時間を作らない |
| **`open -e` でエディタ経由で書かせる** | ヒアドキュメントだとシェル履歴にパスワードが残る |
| **Claude Code に `Read(~/.marketik-wp)` の拒否ルール** | AIが誤って読み上げるのを防ぐ。`deny` は trust 待ちなしで即時適用される |
| **国外アクセス制限は ON のまま** | 制限を緩める方向の回避策は取らない。VPNを切って国内から繋ぐ |

### `wp-draft.py --check` を追加した理由

セットアップの動作確認手段が「テスト記事を作って消す」しかなく、
初めての人には不安が大きかった。`--check` は **何も投稿せず**に
接続・認証・権限・カテゴリ一覧を表示する。

`GET /wp-json/wp/v2/users/me?context=edit` で自分のロールを取得し、
`administrator` / `editor` / `author` が含まれていたら警告を出す。
**権限設定を間違えたまま運用が始まるのを、セットアップ時点で止める。**

モックサーバーで6ケース検証済み（寄稿者・管理者警告・roles欠落時・
401の案内・引数なし・http拒否）。

## Phase 2：Claude連携（2026-09-19）

### 方式の決定：MCPではなく標準REST API

Claude Desktop + WordPress MCP は採用しない。理由：

- `Automattic/wordpress-mcp` は **2026年1月にアーカイブ済み**。後継の
  `WordPress/mcp-adapter` に移行中で、まだ枯れていない
- `@automattic/mcp-wordpress-remote` を使う場合、**本番サイトに MCP Adapter
  プラグインのインストールが必須**。加えて Node.js 22+ が要る
- 「プラグインは資産ではなく負債」というこれまでの判断基準と一貫しない

採用する方式：**WordPress標準のREST API + アプリケーションパスワード。**
本番サイトへの追加インストールはゼロ。

（初期状態のまま。公式マニュアルどおり）。日本国内のIPからなら通るため、

### 連携用アカウント

| 項目 | 値 |
|---|---|
| ユーザー名 | `claude-bot` |
| 権限 | **寄稿者（Contributor）** |
| 認証 | アプリケーションパスワード（発行済み。値はリポジトリに置かない） |

寄稿者を選んだのは、**WordPress側が仕組みとして公開を拒否する**ため。
「下書きまで自動、公開は人が確認」という方針を設定レベルで強制する。

### `wp-draft.py`

記事ファイル（frontmatter + HTML本文）を下書きとして投稿するスクリプト。
接続情報は環境変数または `~/.marketik-wp`（KEY=VALUE、chmod 600）から読む。
**リポジトリには認証情報を置かない。**

安全のための作り：

- `status` は `"draft"` のハードコード。frontmatter に `status: publish` と
  書いても無視される（寄稿者権限と合わせて二重の安全弁）
- slug を検査：半角英小数字ハイフンのみ、予約語（blog/service/works 等）と
  数字のみを拒否。**works の既存スラッグが日本語で文字化けしている失敗を
  ブログで繰り返さないため**
- カテゴリは名前の完全一致で解決し、無ければ中断する（勝手に作らない）
- パスワードを一切出力しない
- 401/403/接続不可それぞれに、原因の見当がつく日本語メッセージを出す

#### 検証内容（モックサーバーで実行）

WordPress REST API を模したローカルサーバーを立てて実際に通した。

- 正常系：draft で POST され、カテゴリIDが解決される
- `status: publish` を frontmatter に書いても draft のまま送信される
- 異常系：日本語slug / 予約語slug / 数字のみslug / slug空 / 存在しない
  カテゴリ / frontmatter不正 / 本文空 / 認証失敗401 / 接続不可
  — すべて意図したメッセージで停止する

### 本番環境での検証結果（2026-09-20）

marketik.jp に対して実際に実行して確認した内容。

#### 連携ユーザーの権限（`GET /wp/v2/users/me?context=edit`）

| ケーパビリティ | 状態 |
|---|---|
| `edit_posts` | あり |
| `publish_posts` | **なし**（安全弁として意図どおり） |
| `upload_files` | **なし** |
| `edit_published_posts` | なし |
| `aioseo_page_analysis` | あり |
| `aioseo_page_general_settings` | あり |

#### AIOSEO はREST API経由で設定できる

**「標準の posts エンドポイントでは設定できない」という当初の想定は誤りだった。**
AIOSEO は独自の名前空間 `aioseo/v1` を公開しており、寄稿者権限のまま書き込める。

```
POST /wp-json/aioseo/v1/post
{"id": 161, "postId": 161, "title": "SEOタイトル", "description": "メタ説明"}
→ {"success": true, "posts": 161}
```

投稿160・161の両方で成功し、投稿一覧の「AIOSEO 詳細」列に反映されることを確認済み。
**メタディスクリプションの手入力は不要。**

注意点：

- 書き込みは成功するが、`GET /aioseo/v1/post` から保存値を読み出す方法は未確立。
  反映確認は管理画面か投稿一覧の「AIOSEO 詳細」列で行う
- `_aioseo_*` は `wp/v2/posts` の `meta` には現れない（独自テーブル管理のため）

#### 本文HTMLは寄稿者権限でも削られない

`unfiltered_html` を持たないため kses が適用されるが、記事テンプレートが推奨する
タグ（`p` `h2` `h3` `ul` `li` `strong` `a`）は全て通過した。
外部リンクの `target="_blank"` `rel="noopener"` も残る。

### できないこと・積み残し

- **アイキャッチ画像は設定できない。** `upload_files` が無いため `POST /wp/v2/media`
  が使えない。画像は管理画面で手動アップロードする。
  自動化するなら投稿者権限への変更ではなく、寄稿者に `upload_files` だけを追加する：

  ```php
  get_role('contributor')->add_cap('upload_files');
  ```

  投稿者権限は `publish_posts` を含むため、二重の安全弁が崩れる
- **slug の重複チェックがない。** 下書き段階では WordPress がスラッグを調整しない
  （`wp_unique_post_slug` が draft を除外する）ため、同じslugの既存記事があると
  公開時に `-2` が付き、スクリプトが表示する「公開後URL」とズレる
- **`WP_URL` が https であることを強制していない。** http を書くとアプリケーション
  パスワードが平文で流れる
